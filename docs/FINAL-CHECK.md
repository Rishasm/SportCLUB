# Итоговая проверка SportCLUB

## Расписание, сотрудники и питание · 6 ноября 2026

- На локальном стенде проверены пять маршрутов, регистрация в Eureka, получение конфигурации, PostgreSQL, OpenAPI и идентификаторы запросов.
- Maven-сборка прошла 45 проверок. Дополнительный тест в PostgreSQL подтвердил, что публиковать объявления может администратор, а клиент получает опубликованное объявление.
- Через Gateway проверены границы календаря, валидация, CRUD расписания, запрет клиенту и тренеру изменять расписание, изоляция занятий тренера, уведомления при переносе и отмене, редактирование профиля и смена пароля.
- Оба способа учебной оплаты работают. Повтор запроса возвращает идентификатор того же абонемента. Тестовую карту можно привязать и отвязать.
- Дневник питания проверен на добавление, изменение и удаление порции, подсчёт КБЖУ по приёмам пищи и за день, отклонение некорректных данных и изоляцию аккаунтов.
- Браузерная проверка прошла для карточки занятия, схемы упражнения, кабинетов сотрудников, помощи, профиля, оплаты и питания. Новые пользовательские страницы проверены на ширине 390 и 320 px.
- При проверке Circuit Breaker остальные четыре маршрута продолжили отвечать HTTP 200, а перезапущенный сервис показателей вернул ту же запись воды с тем же JWT.

## Проверка до расширения · 5 ноября 2026

Локальный стенд использует четыре отдельные базы на одном сервере PostgreSQL. В каждом бизнес-сервисе контроллер вызывает сервис, который обращается к Spring Data JPA-репозиториям. Обязательные и дополнительные пункты задания реализованы.

| Пункт задания | Реализация | Подтверждение |
|---|---|---|
| Не менее трёх микросервисов | Четыре бизнес-сервиса: клиенты, клуб, тренировки, показатели | Отдельные Spring Boot-приложения, API, JPA-репозитории и базы |
| Spring Cloud Config | Native Config Server и обязательный Config Client import | Ответ `localhost:8888/members-service/local`, `configurationSource: config-server` в API |
| Eureka | Реестр и регистрация клиентов | Четыре бизнес-сервиса и Gateway в реестре; межсервисный клиент использует имя сервиса |
| API Gateway | Четыре маршрута `lb://` | Рабочие `/api/members/**`, `/api/club/**`, `/api/workouts/**`, `/api/wellness/**` через порт 8080 |
| Circuit Breaker | Независимые Resilience4j Circuit Breaker на маршрутах | Реальная остановка wellness, метрика OPEN, независимость остальных маршрутов и восстановление |
| Мониторинг и логирование | Actuator health/info/metrics и общий `X-Request-ID` | Доступные метрики, одинаковый идентификатор в ответе, Gateway и логе сервиса |
| Документация API | OpenAPI и Swagger UI каждого бизнес-сервиса | Четыре документа через Gateway, описания операций и Bearer JWT |

`service-foundation` является общей библиотекой; Config Server, Eureka и Gateway — инфраструктурные приложения. Четыре бизнес-сервиса подсчитаны отдельно от них.

## Проверки на PostgreSQL

- Все **45 тестов** прошли. Интеграционные тесты создали изолированные схемы в `sportclub_test` и выполнили HTTP-запросы к сервисам.
- Flyway применил `V1` и `V2` во всех четырёх рабочих базах. Сверены **159 строк** из прежних локальных баз после переноса.
- Во всех четырёх JAR проверены драйвер PostgreSQL и модуль Flyway для PostgreSQL.
- На полном стенде Gateway получил ответы всех четырёх бизнес-сервисов с `database.engine: PostgreSQL`. Проверены Config Server, регистрация в Eureka, OpenAPI и передача `X-Request-ID`.
- Повторный запуск прошёл. Главная страница и диагностика вернули HTTP 200. Через Gateway проверены вход, покупка абонемента и бронирование, дневник тренировок, вода, сон и ИМТ.
- Flyway 11.7.2 выводит предупреждение, что PostgreSQL 18.3 новее проверенной им версии. Миграции и интеграционные тесты на установленной 18.3 прошли.

- Полный запуск на копиях прежних баз. Hibernate проверил существующие таблицы. Сравнение после остановки подтвердило сохранность каждой строки из резервной копии.
- Реальные API-сценарии: вход, абонемент и запись; дневник тренировок; вода, сон и ИМТ.
- Браузерные сценарии этих трёх частей, перезагрузка страницы, повторный вход и изоляция личных данных.

## Проверка отказа и восстановления

Для работающего локального стенда:

```powershell
.\scripts\test-resilience.ps1
```

Сценарий проверяет Config Server и Eureka, сохраняет отдельную тестовую запись воды, останавливает только Java-процесс `wellness-service` из манифеста проекта и восстанавливает его в `finally`.

Фактический результат:

1. Недоступный маршрут показателей вернул **503**, `code: SERVICE_UNAVAILABLE`, `service: wellness` и тот же `X-Request-ID`.
2. Метрика `resilience4j.circuitbreaker.state` с тегами `name:wellness`, `state:open` показала **1**.
3. Счётчик вызовов, отклонённых открытым Circuit Breaker, вырос **с 0 до 3**.
4. Клиенты, клуб и тренировки продолжили возвращать **200**; их Circuit Breaker остались CLOSED.
5. После восстановления показатели вернулись к **200/CLOSED**.
6. Тот же JWT открыл ту же сохранённую порцию 250 мл с прежним идентификатором. Тестовая порция затем удалена.
7. PID остальных шести приложений не изменились.

Последний результат сохраняется в `.runtime/resilience-result.json`. Последующие успешные прогоны могут иметь другие абсолютные значения счётчиков; сценарий проверяет их рост.

Для отдельного перезапуска бизнес-сервиса предусмотрен проверенный скрипт:

```powershell
.\scripts\restart-local-service.ps1 -Name wellness-service
```

Он проверяет точный jar, PID и порт, обновляет манифест, ждёт health и сохраняет базы. Доступны также `members-service`, `club-service`, `workouts-service`; весь стенд должен быть запущен заранее.

## Границы текущей реализации

Config использует локальные YAML в native-режиме. Изменения применяются при следующем запуске клиента; горячий refresh и Git-репозиторий конфигурации не подключены. Цвет сайта задан в CSS; Config централизует серверные параметры, включая маршруты, базы, тайм-ауты, логи и служебные настройки бренда.

Мониторинг базовый: Actuator и корреляция логов. Отдельные Prometheus, Grafana и распределённый tracing не подключены. Circuit Breaker настроен на Gateway; внутренний запрос проверки абонемента защищён тайм-аутами и обработкой недоступности.

Рабочие базы `sportclub_members`, `sportclub_club`, `sportclub_workouts` и `sportclub_wellness` находятся на локальном сервере PostgreSQL. Flyway применяет миграции в каждой базе, Hibernate сверяет сущности с таблицами. Интеграционные тесты используют отдельную базу `sportclub_test`.
